# Knowledge Transfer: v0.1

Everything you need to own this codebase as of `v0.1.1`: what each part does, why
it was built that way, where the code lives, how to debug it, and exercises that
prove you understand it.

**How to use this doc.** Read sections 1 to 3 first (about 30 minutes). Then do the
exercises in section 9 with the code open; they take about 2 hours and are what
turns reading into ownership. Sections 4 to 8 are reference.

---

## 1. The project in 60 seconds

> I built an agent that answers business questions over a Postgres warehouse by
> writing SQL. The hard part of text-to-SQL is not SQL syntax, it's meaning: the
> schema doesn't tell you that "revenue" excludes cancelled orders or that a status
> value is lower case. So the agent first retrieves the relevant metric definitions
> and table docs (RAG), then writes SQL against only the relevant tables, runs it
> through a read-only MCP server, and answers with citations. On a 30-question
> benchmark, retrieval raised execution accuracy from 57% to 90-100%. Read-only
> access is enforced by Postgres roles, not by the prompt.

The demo GIF in the README shows exactly this: the baseline guesses
`status = 'Completed'` (the real value is `'completed'`) and returns nothing; the RAG
version returns $16,284,419.72 with the metric cited; a `DELETE` is rejected by
Postgres.

## 2. Architecture

```text
                         ┌──────────────────────── agent process ───────────────────────┐
 question ──► CLI/eval ──► AnalyticsAgent.ask()                                         │
                         │   1. build_context ──► knowledge_search_knowledge ──┐         │
                         │                    ──► warehouse_describe_table     │         │
                         │   2. chat_json(generate_sql) ──► LLM (Gemini/OpenAI)│         │
                         │   3. warehouse_run_query ─────────────────────┐     │         │
                         │   4. chat_json(answer) ──► LLM                │     │         │
                         └───────────────────────────────────────────────┼─────┼─────────┘
                                         MCP over stdio (JSON-RPC)       │     │
                         ┌──────────── warehouse-mcp ────────┐  ┌──── knowledge-mcp ────┐
                         │ list_tables / describe_table /    │  │ search_knowledge       │
                         │ run_query (LIMIT, 1 statement)    │  │ get_documents          │
                         └──────────────┬────────────────────┘  └──────────┬─────────────┘
                                        │ role agent_readonly               │ role knowledge_reader
                         ┌──────────────▼───────────── Postgres 17 + pgvector ─▼──────────┐
                         │ schema analytics (8 tables, ~900k rows)  schema knowledge.chunks│
                         └────────────────────────────────────────────────────────────────┘
 offline: data/seed/generate.py ──► analytics      ingestion/ingest_docs.py ──► knowledge
```

### One request, step by step (`make ask Q="What was net revenue in 2024?"`)

1. `agent/__main__.py` builds an `AnalyticsAgent` with the `rag` feature config.
2. `AnalyticsAgent.__aenter__` opens one fastmcp `Client` over **both** servers from
   `config/servers.yaml`. fastmcp spawns each server as a subprocess (stdio) and
   prefixes tool names with the server name: `warehouse_run_query`.
3. `build_context` (`agent/loop.py:90`) calls `knowledge_search_knowledge` with the raw
   question, k=6. The knowledge server embeds the question with bge-small and runs a
   pgvector cosine search. Top hit here: `metric:net_revenue`.
4. **Schema linking.** It collects `table_names` from the retrieved chunks and calls
   `describe_table` only for those (cached per agent). The model never sees the full
   schema in RAG mode.
5. `chat_json` (`agent/llm.py:111`) sends the `generate_sql.md` prompt plus CONTEXT and
   asks for JSON: `{sql, tables_used, chunk_ids_used, assumptions}`.
6. `warehouse_run_query` runs the SQL: `prepare_query` checks it's one statement and
   adds `LIMIT max_rows + 1`; Postgres runs it as `agent_readonly`.
7. A second `chat_json` call with `answer.md` turns rows into a short answer with
   citations and caveats (known data issues).
8. `AgentAnswer` carries everything: SQL, rows, retrieved chunk ids and scores,
   per-step timings, tokens, cost.

The `baseline` config skips step 3 and describes **every** table instead. That is the
only difference between the two rows of the results table.

## 3. Components

### 3.1 Postgres and the roles: `infra/`

- Image `pgvector/pgvector:pg17`, port 5433 (avoids clashing with a local 5432).
- `01_schemas_and_roles.sql` creates two schemas and two login roles:

| Role | Used by | Can read | Settings |
|---|---|---|---|
| `agent_readonly` | warehouse-mcp | `analytics` only | read-only transactions, 10s statement timeout, 30s idle-in-transaction timeout |
| `knowledge_reader` | knowledge-mcp | `knowledge` only | read-only transactions, 5s statement timeout |
| `postgres` | seeding, ingestion | everything | admin, never used by servers |

- `ALTER DEFAULT PRIVILEGES` (line 19) grants SELECT on tables created **later** by
  `postgres`. Without it, the grant would only cover tables that already existed when
  the script ran.
- Init scripts run once, when the data volume is empty. Changing them needs
  `make reset bootstrap`.

**Why roles and not prompt rules:** a prompt is a suggestion to the model; a role is
a guarantee from the database. Four independent layers stop a write: the
single-statement parser check, read-only transactions, SELECT-only grants, and the
timeout. Layers 2 and 3 each stop it alone. Proven in `tests/test_servers_db.py`
(including a `DELETE` hidden inside a CTE, which passes the parser).

### 3.2 Synthetic data: `data/seed/generate.py`

- Fixed seed 42, so every run produces identical data. Gold SQL answers never drift.
- About 901k rows: 50k customers, 300 products, 200k orders, ~447k order items,
  ~186k payments, ~13k refunds, plus a deprecated `legacy_orders_v1`.
- Realism: order dates skew later (growth) with a Q4 bump; customer popularity is
  Pareto-like so repeat-customer metrics mean something.
- **Planted traps** used by evals: NULL `channel` before 2023-03-01 (ISSUE-001), NULL
  refund `reason` before 2024 (ISSUE-002), ~2% customers without a region
  (ISSUE-003), a deprecated table, an outdated 2022 revenue guide, and two conflicting
  "active customer" definitions.
- Loads with Postgres `COPY` (fast: ~4.5s for 900k rows) after `TRUNCATE ... CASCADE`,
  so re-running is safe.

### 3.3 Knowledge sources: `data/docs/`

| Folder | Format | Chunk id | Count |
|---|---|---|---|
| `tables/schema.yml` | dbt `schema.yml` style | `table:analytics.orders` | 8 |
| `metrics/metrics.yml` | name, synonyms, description, SQL, tables | `metric:net_revenue` | 10 |
| `issues/*.md` | front matter + body | `issue:ISSUE-001` | 3 |
| `glossary/*.md` | front matter + body | `glossary:marketing-glossary` | 2 |

The metric definitions are the heart of the RAG uplift. Example: `net_revenue` says
gross revenue is attributed by `order_date` but refunds by `refunded_at`. No schema
contains that rule.

### 3.4 Ingestion: `ingestion/`, `common/embeddings.py`

- **Structure-aware chunking** (`ingestion/chunking.py`): one chunk per table, metric,
  issue or glossary doc, not fixed-size windows. A retrieved chunk is always a
  complete, citable unit. Deprecated and outdated sources get a warning prefix in the
  chunk text so the model sees it (`DEPRECATED`, `OUTDATED DOCUMENT.`).
- **Metadata:** `table_names` (drives schema linking and recall@k), owner, dates,
  flags in `metadata` JSONB.
- **Embeddings:** `BAAI/bge-small-en-v1.5` via fastembed: ONNX, runs on CPU, no API
  key, 384 dimensions. `passage_embed` for documents and `query_embed` for questions
  (bge is an asymmetric model: queries and passages are encoded differently).
- **Idempotent upsert** (`ingest_docs.py:28`): compare each chunk's SHA-256 content
  hash with what's stored; embed only changed chunks; delete chunks whose source
  disappeared. Second run: "0 embedded, 23 unchanged".
- **Index:** HNSW with `vector_cosine_ops` (`02_tables.sql:82`). At 23 chunks it doesn't
  matter; it's there so the design holds at 100k chunks.

### 3.5 MCP in one page

MCP (Model Context Protocol) is a JSON-RPC protocol that lets any client (Claude
Desktop, Cursor, your own agent) discover and call tools on a server.

- **Tools** have a name, description, JSON input schema and (here) an **output schema**
  from the Pydantic return types. Clients get typed `structured_content`, not just text.
- **Tool annotations** (`readOnlyHint`, `destructiveHint`, `idempotentHint`,
  `openWorldHint`) tell clients how risky a tool is. All five tools here are read-only.
- **Server instructions**: the `instructions=` text on each `FastMCP(...)` is sent to
  clients at initialization; it tells the model how to use the server.
- **Transports:** stdio (client spawns the server as a subprocess; used by the agent
  and Claude Desktop) and Streamable HTTP (`--transport http`, `make serve-warehouse`).
- **Errors:** raising `ToolError` returns `isError: true` with a message the model can
  read and act on, instead of crashing the session.
- **Multi-server client:** fastmcp's `Client({"mcpServers": {...}})` connects to many
  servers and namespaces tools as `<server>_<tool>`.

### 3.6 warehouse-mcp: `servers/warehouse_mcp/`

| Tool | What it does | Notes |
|---|---|---|
| `list_tables(schema)` | tables + row estimates from `pg_class.reltuples` | filters with `has_table_privilege`, so it only lists what the role can read |
| `describe_table(table)` | columns, types, nullability | accepts `orders` or `analytics.orders`; parameterized query, no SQL injection |
| `run_query(sql, max_rows)` | rows + `truncated`, `sql_executed`, `elapsed_ms` | max_rows capped at 1000 |

`prepare_query` (`sql.py:19`) uses sqlglot to:
1. reject more than one statement,
2. inject or lower `LIMIT` to `max_rows + 1`. The extra row is how `truncated` is
   detected without a second COUNT query.
3. pass non-queries and unparseable SQL through **unchanged**, on purpose: the database
   is the enforcement layer and returns the real error.

Postgres errors become `ToolError("Database error: ...")` with the primary message
and hint, which the model can use to fix its SQL (self-correction arrives in v0.3).

### 3.7 knowledge-mcp: `servers/knowledge_mcp/`

- `search_knowledge(query, k, source_types)`: embeds the query, orders by
  `embedding <=> query` (cosine distance), returns `score = 1 - distance`.
  `source_types` filters to table, metric, issue or glossary.
- `get_documents(chunk_ids)`: exact fetch by id.
- `main()` warms the embedding model before accepting requests, so the first search
  isn't slow.

### 3.8 The agent: `agent/`

- `loop.py` is the whole orchestration, about 180 lines, no framework (ADR-002).
  - `_tool()` wraps every MCP call and turns `isError` into `ToolCallError`.
  - `build_context()` is RAG plus schema linking (section 2, steps 3 and 4).
  - `ask()` runs the steps, records `timings_ms` per step, and catches both
    `ToolCallError` and provider `APIError` so one bad question never kills an eval.
- `prompts/generate_sql.md` rules that matter: use only CONTEXT tables, follow governed
  metric definitions exactly, ignore DEPRECATED/OUTDATED sources, no PII columns,
  **don't round** (the comparator rounds), no ORDER BY/LIMIT unless asked.
- JSON mode (`response_format={"type": "json_object"}`) keeps output parseable;
  `_parse_json` also strips Markdown code fences, since some providers add them.

### 3.9 The LLM layer: `agent/llm.py`, `common/settings.py`

- Every provider speaks the OpenAI chat-completions API, so one SDK covers OpenAI,
  Azure, Gemini (OpenAI-compatible endpoint) and Ollama. `LLM_PROVIDER` selects a
  preset in `settings.PROVIDERS`.
- **Rate limits:** `_Throttle` spaces calls to `LLM_RPM` (14 for Gemini Flash Lite's
  free 15 RPM); the SDK retries 429/5xx up to 8 times with backoff.
- **Cost:** tokens × list price from `LIST_PRICES`, or "n/a" when the price is unknown.
  Reported as what the run *would* cost on a paid plan.

### 3.10 Config: `config/`

- `servers.yaml` is the MCP server registry. **A new server is a config entry, not
  code.** `QUIET_ENV` (`agent/config.py:13`) silences server logs; to debug a server,
  add `env: {FASTMCP_LOG_LEVEL: DEBUG}` to its entry.
- `features.yaml` holds named feature-flag sets. Each name is one results row.
  `baseline` = `rag: false`; `rag` = `rag: true, k: 6`.

### 3.11 Evals: `evals/`

- `questions/v0_1.yaml`: 30 questions with gold SQL and `expected_tables`. Categories:
  simple (10), joins (8), aggregation (8), filters (4).
- **Execution accuracy** (`metrics/compare.py`): run gold and predicted SQL and
  compare result sets, not SQL strings. Two different queries can both be right.
  Rules: row order ignored; numbers rounded to 4 decimals; midnight timestamps equal
  dates; extra predicted columns allowed if a subset matches exactly; row counts must
  match; a gold year, quarter or month number may match a predicted date label for the
  same period. Text labels are never remapped (that could accept swapped labels).
- **Table recall@5** (`metrics/retrieval.py`): share of the tables the gold SQL needs
  that appear in the top 5 retrieved chunks. It measures retrieval separately from
  generation, so you can tell which half failed.
- **Runner** (`runners/run_eval.py`): one agent session for all questions; gold
  queries on an autocommit connection; writes `results/<version>-<config>-<model>.json`
  (committed) and `.jsonl` per-question detail (gitignored). `--only` runs go to
  `results/partial/` and never touch the README numbers. `--check-gold` runs gold SQL
  without an LLM.
- `scripts/make_results_table.py` rewrites the README table between the
  `RESULTS:START/END` markers. Numbers are never typed by hand.

### 3.12 Tests and tooling

- 36 tests: SQL preparation, comparator rules, chunking, and integration tests that
  call the real servers through an in-memory fastmcp `Client` (no subprocess).
  `pytest -m "not db"` runs without Postgres.
- `make tool S=warehouse T=run_query A='{"sql":"SELECT 1"}'` calls any tool through
  real MCP. `make tools` lists them. Best debugging aid in the repo.
- `docs/demo.tape` regenerates the README GIF with VHS.

## 4. Design decisions and trade-offs

| Decision | Why | Rejected alternative | Cost of the choice |
|---|---|---|---|
| Two servers split by trust boundary (ADR-001) | A bug or injection in retrieval cannot read warehouse rows | One server; or one per feature (catalog, dbt, tickets) | Two processes to start |
| Read-only enforced by Postgres roles | Guarantee instead of suggestion; survives prompt injection | Regex/AST checks only | Needs DB admin setup |
| Small explicit loop (ADR-002) | Each step visible, timed, flag-switchable, explainable | LangChain / LangGraph | Branching (v0.3) is hand-written |
| Structure-aware chunks | Each hit is a whole, citable unit | Fixed 512-token windows | Very long docs would need splitting later |
| Schema linking from retrieved chunks | Scales to hundreds of tables; less noise | Paste the full schema | If retrieval misses a table, SQL can't use it (recall@5 tracks this) |
| Local embeddings (fastembed bge-small) | Free, offline, no key, fast | OpenAI embeddings | Lower quality than large API models; fine at this scale |
| pgvector in the same Postgres | One system to run; SQL filters plus vectors | Pinecone, Qdrant | Fewer ANN tuning knobs |
| Execution accuracy (result sets) | Different SQL can be equally correct | Exact SQL string match | Comparator rules must be documented |
| OpenAI-compatible LLM layer | Swap providers by env var; enables model comparison | Provider SDKs | Provider-specific features (Gemini thinking budgets) unused |
| Deterministic synthetic data | Stable gold answers, shareable, no PII | Public dataset | Less messy than real data |

## 6. Bugs found during v0.1 (your war stories)

Each of these is a good answer to "tell me about a bug you found".

1. **Idle-in-transaction kill.** The eval runner kept one gold-query connection open in
   a transaction. When rate-limit retries made a question wait more than 30s, Postgres's
   `idle_in_transaction_session_timeout` (a guardrail set in v0.1 itself) killed the
   connection and the whole run crashed. Fix: autocommit for read-only gold queries.
   Lesson: your own guardrails will find your own bugs.
2. **One provider error killed the run.** A 503 "high demand" after all retries escaped
   `ask()`. Fix: catch `APIError` per question, record it as a failure, continue.
3. **Partial runs overwrote real results.** `--only q026` wrote a one-question summary
   over the 30-question file. Fix: partial runs write to `results/partial/`.
4. **Comparator false negative.** The model labeled quarters as dates (`2023-01-01`)
   while gold used numbers (`1`); counts were right. Fix: a narrow date-to-period
   transform; general label remapping rejected because it could accept wrong answers.
5. **Ambiguous test questions.** "Customers per region" vs a doc saying 2% have no
   region: the model sometimes added an "Unassigned" bucket, arguably the better answer.
   Fix: clarified the wording and logged the change in the CHANGELOG, because editing a
   test set after seeing results must be disclosed.
6. **Retired model.** `gemini-2.5-flash` returned 404 for new users; the 429 error body
   (not headers) revealed the real per-minute quota. Fix: model probing, presets.

## 7. Limitations and what's next

| Limitation | Why it matters | Planned |
|---|---|---|
| Vector-only retrieval | Exact terms (`refund_rate`, `ISSUE-003`) can rank lower than paraphrases | v0.2: BM25 + vector, RRF, reranker |
| One run per config | Gemini varies even at temperature 0 (90-100%) | v0.2: N runs, mean and range |
| No clarification or self-correction | Ambiguous questions get guessed; SQL errors aren't retried | v0.3 |
| Free SQL, no semantic layer | Metric logic re-derived by the model each time | v0.3: compile governed metrics |
| One shared DB role | No per-user permissions, PII readable if asked | v0.4: OAuth to RLS, masking |
| 30 questions | Too small for strong claims | grows to ~150 by v1.0 |
| Prompt injection via docs | Retrieved text goes straight into the prompt | v0.4 |

## 8. Operating and debugging

```bash
make bootstrap        # first time: deps, .env, Postgres, data, embeddings
make up / make down   # start / stop Postgres (data kept)
make reset bootstrap  # wipe and rebuild (after changing infra/db/init)
make tools            # list MCP tools
make tool S=knowledge T=search_knowledge A='{"query":"refund rate","k":3}'
make ask Q="..." CONFIG=rag|baseline
make check-gold       # gold SQL sanity, no LLM
make eval CONFIG=rag  # one config; make eval-all for both
make test / make lint
```

| Symptom | Likely cause | Fix |
|---|---|---|
| `connection refused` on 5433 | Postgres not running | `make up` |
| `permission denied for table` | Table created after the role, or the wrong role | Check `ALTER DEFAULT PRIVILEGES`; `make reset bootstrap` |
| Search returns nothing or stale results | Docs changed but not re-ingested | `make ingest` |
| `No API key for LLM_PROVIDER=...` | Key not in `.env` for that provider | Add the key; check `LLM_PROVIDER` |
| 404 from Gemini | Model retired for new accounts | Set `LLM_MODEL` to a model from the AI Studio rate-limit page |
| Many 429s or slow eval | Free-tier RPM | Lower `LLM_RPM` |
| Eval accuracy drops | Model variance or a real regression | Compare `.jsonl` files per question; rerun the failing ids with `--only` |
| A tool fails silently | Server logs are muted | Set `env: {FASTMCP_LOG_LEVEL: DEBUG}` for it in `servers.yaml` |

To see exactly what the model saw: `uv run python -m agent "..." --json` prints the
retrieved chunk ids, tables in context, SQL, timings and tokens.

## 9. Exercises (do these to own it)

Do them in order with Postgres running. Each says what you should observe.

1. **Trace a request.** Run `make ask Q="What was the refund rate for orders placed in
   2024?" CONFIG=rag` and the same with `--json` via `uv run python -m agent`. Find the
   retrieved chunks, the tables in context and the per-step timings. Explain which
   chunk made the SQL correct.
2. **Break read-only, three ways.** With `make tool`, try `DELETE`, `DROP TABLE` and the
   CTE trick `WITH d AS (DELETE FROM analytics.orders RETURNING *) SELECT count(*) FROM d`.
   Name the layer that stopped each one.
3. **Prove schema linking.** Ask a question about payments with `--json`. Confirm that
   `tables_in_context` excludes unrelated tables. Then run the baseline and compare
   context size (input tokens).
4. **Change a definition.** Edit `gross_revenue` in `data/docs/metrics/metrics.yml` to
   include `placed` orders. Run `make ingest` (expect exactly 1 chunk re-embedded), ask
   about 2024 gross revenue, and watch the SQL change. Revert and re-ingest.
5. **Add a metric.** Add `cancellation_rate` to `metrics.yml`, ingest, ask about it, and
   add a question with gold SQL to the eval set. Run `make check-gold`.
6. **Retrieval only.** `make tool S=knowledge T=search_knowledge A='{"query":"how is
   active customer defined","k":5}'`. Two conflicting definitions come back: which
   ranks higher, and what tells the model which one to use?
7. **Read a failure.** Open `evals/results/v0.1-baseline-*.jsonl`, pick a failing
   question and explain in one sentence why the baseline got it wrong.
8. **Comparator rules.** Add a test to `tests/test_compare.py` showing that a predicted
   answer with an extra id column passes, and one with a missing row fails.
9. **Swap the model.** Set `LLM_MODEL=gemini-3.1-flash-lite`, run
   `make eval CONFIG=rag`, and compare the new results row. (Uses ~30 requests.)
10. **Add an MCP server.** Write a 15-line FastMCP server with one tool (say,
    `get_server_time`), register it in `config/servers.yaml`, and see it in
    `make tools` without touching agent code.

## 10. Glossary

| Term | Meaning here |
|---|---|
| Governed metric | A definition owned by a team and treated as the single source of truth |
| Schema linking | Picking which tables and columns are relevant to a question |
| Execution accuracy | Predicted SQL returns the same result set as gold SQL |
| Recall@k | Share of the needed items found in the top k retrieved |
| HNSW | Graph-based approximate nearest-neighbour index used by pgvector |
| Asymmetric embedding | Query and passage encoded differently (bge `query_embed` vs `passage_embed`) |
| Tool annotations | MCP hints about a tool's risk: read-only, destructive, idempotent |
| Structured output | MCP tool results with a JSON schema, not just text |
| Ablation | Turning one feature off to measure what it contributes |
| Trust boundary | Line between components with different access to sensitive data |
